# 项目系统提示词：Kustom 式开源 Android 动态壁纸编辑器

## 0. 项目定位（不可动摇的前提）

你正在协助开发一个 **Android 平台的动态壁纸创作工具**，定位是“移动端的 KLWP 替代品”。
产品路径是：**先做单机编辑器工具 → 预设文件可导出/导入 → 社区通过 GitHub Discussions 交换预设 → 长期自然生长为平台**。

**明确约束：**
- **不搞商业**。没有订阅、没有广告、没有内购。接受赞助（如 GitHub Sponsors / 爱发电），但赞助不能换取功能特权或闭源授权。
- **开源**。许可证使用 **Apache 2.0**，保留专利授权与未来平台服务层闭源的可能性。
- **只做 Android**。iOS 的“真动态壁纸”在系统层面不成立，不在本项目范围内。
- **引擎优先于 UI**。在编辑器 UI 完善之前，预设格式 Schema、渲染引擎、交互事件总线必须先稳定。

## 1. 技术栈硬性约定

- 语言：**Kotlin**
- 渲染：**OpenGL ES 2.0** 起步（兼容性优先），架构上为 ES 3.0 留好接口。不引入重型游戏引擎（Unity/Unreal），保持包体轻量与开源可维护性。
- 壁纸宿主：**`WallpaperService` + `WallpaperService.Engine`**。引擎必须实现 `onVisibilityChanged`，在壁纸不可见时 **完全停止 GPU 绘制和传感器监听**，这是移动端功耗的红线。
- 触摸事件：通过 `setTouchEventsEnabled(true)` 启用，在 `onTouchEvent(MotionEvent)` 中接收原始触摸事件，并归一化为引擎内部的交互事件。
- 数据格式：**JSON**。预设包、场景图、交互逻辑图、全局变量定义，全部用 JSON 描述。参考 Lucid Fork LWP 的 JSON 脚本思路，但 Schema 必须由本项目**自己定义并开源**[reference:1]。

## 2. 三大交互系统的提示词定义

这是本项目的核心。任何交互能力都必须以 **“事件源 → 条件/修饰 → 动作/动画”** 的统一模型表达，**不允许在引擎中硬编码某个具体交互逻辑**。

### 2.1 动画交互（Animation Interaction）

**目标**：让用户通过时间轴和缓动曲线，驱动元素的属性变化，并让动画可被外部事件触发或打断。

**必须暴露给编辑器的能力：**
- 属性可动画化：位置（X/Y）、缩放、旋转、透明度、颜色、裁剪、3D 变换（旋转/透视/视差）。
- **动画时间轴**：支持关键帧、缓动曲线（ease-in/out/cubic-bezier）、循环模式（once/loop/pingpong）。
- **触发器类型**：触摸按下/抬起、屏幕滚动（`onOffsetsChanged`）、传感器变化、系统广播、全局变量变化。
- **打断与混合**：当一个动画正在播放时，新触发器到达应能定义“覆盖 / 叠加 / 排队”策略。

**引擎内部数据模型（必须实现的 JSON 结构片段）：**
```json
{
  "type": "animation",
  "targetId": "element_001",
  "property": "rotationZ",
  "keyframes": [
    {"t": 0.0, "value": 0, "easing": "cubicOut"},
    {"t": 0.6, "value": 15, "easing": "linear"},
    {"t": 1.0, "value": 0, "easing": "cubicInOut"}
  ],
  "durationMs": 800,
  "loop": "once"
}
明确不做的：不在 MVP 阶段实现类似 KLWP 公式系统那样的“图灵完备”文本表达式。动画参数通过可视化时间轴 + 数值输入完成，保持 JSON Schema 的确定性和可验证性。

2.2 软件交互（Software / App Interaction）
目标：让壁纸元素能够响应用户手势并执行 App 级别的动作，而不是只能“看”。

必须支持的触摸动作（Touch Actions）：

点击元素 → 启动指定应用（Intent，需处理包名不存在时的优雅降级）。

点击元素 → 切换壁纸全局状态（例如切换主题、开关某个图层组）。

点击元素 → 触发自定义动画序列（串联多个动画节点）。

长按 / 双击 → 绑定不同的动作。

触摸位置 → 作为粒子/着色器的输入参数（触摸点坐标传递到 GLSL uniform）。

手势与屏幕滚动：

接入 onOffsetsChanged，将桌面滑动偏移量归一化后驱动视差、位移或着色器参数。

支持多指触摸的简化抽象（至少识别单指/双指，不追求完整手势识别器）。

软件交互的“动作节点”在 JSON 中的表达：

json
{
  "id": "touch_action_01",
  "event": "tap",
  "targetId": "element_001",
  "actions": [
    {"type": "launchApp", "package": "com.example.app"},
    {"type": "setGlobalVar", "name": "theme_mode", "value": "dark"},
    {"type": "playAnimation", "animationId": "anim_pulse"}
  ]
}
边界说明：KLWP 本身不支持直接播放音频/音效，需要借助 Tasker 等第三方应用。本项目第一版也不做音频播放，保持引擎纯粹。但动作节点 Schema 中预留 "type": "broadcastIntent"，为未来与 Tasker/自动化应用桥接留好扩展点。

2.3 系统交互（System Interaction）
目标：让壁纸感知设备状态，并让这些状态成为动画和逻辑的输入源。

必须接入的系统数据源（通过 BroadcastReceiver / SensorManager / 系统服务）：

类别	数据源	引擎内的规范化变量名
电池	ACTION_BATTERY_CHANGED（电量百分比、充电状态）	sys.battery.level, sys.battery.charging
电源	ACTION_POWER_CONNECTED / DISCONNECTED	sys.power.connected
屏幕	ACTION_SCREEN_ON / OFF	sys.screen.on
网络	CONNECTIVITY_CHANGE / WIFI_STATE_CHANGED	sys.net.type, sys.net.connected
时间	系统时钟（分钟级更新，由引擎自身定时器驱动）	sys.time.hour, sys.time.minute
传感器	Sensor.TYPE_ACCELEROMETER / GYROSCOPE	sensor.accel.x/y/z, sensor.gyro.x/y/z
音乐	可选（MediaSessionManager，需权限引导）	media.isPlaying, media.title
天气/位置	第一版不做。KLWP 的天气/位置集成依赖外部数据源和权限，引入会拖慢引擎闭环。Schema 中预留占位即可。	
上述广播的触发时机是 Android 系统的标准行为：屏幕亮灭、电量变化、电源插拔、网络切换都会发出对应广播，引擎侧只需注册接收并更新内部变量表。

系统交互的使用方式：系统变量进入引擎后，与动画和软件交互共用同一套“变量驱动”模型。例如，用户可以在动画时间轴中把 sys.battery.level 绑定为某个元素的缩放输入，或者写一条简单规则“当 sys.power.connected 变为 true 时，触发一次颜色过渡动画”。不要求用户在 JSON 里写代码，规则通过可视化规则行（Rule Row）配置。

3. 编辑器 UI 的硬性约束（防止在手机上复刻桌面复杂度）
编辑器采用三层渐进披露结构，每一层都必须能独立完成一次“修改→预览→保存”的闭环：

第 1 层：画布 + 属性面板（默认视图）

所见即所得画布，支持拖拽元素、双指缩放画布。

点选元素后，底部属性面板直接调整颜色、大小、位置、基础透明度。

覆盖 80% 的轻度自定义需求。

第 2 层：时间轴 / 规则面板（进阶视图）

从属性面板的“动画”入口进入。

时间轴用水平轨道 + 关键帧点表达，缓动曲线用可视化曲线选择器，不要求用户输入贝塞尔控制点。

系统交互和软件交互以规则行呈现：“当 [事件] 发生时，对 [目标] 执行 [动作]”。事件和动作都从下拉列表选择，不允许自由文本输入。

第 3 层：全局变量与预设管理（系统视图）

全局变量的定义、默认值、类型（数值/颜色/布尔/字符串）。

预设的导出（打包为 .zip 或自定义扩展名）与导入。

版本号、引擎最低兼容版本、作者信息。

反模式禁止：不在手机上实现节点连线式逻辑图编辑器。节点图在桌面端是合理的，在手机小屏上会迅速不可用。规则行 + 时间轴的组合，在表达力和可操作性之间取得了更适合移动端的平衡。

4. 预设文件格式（从第一天就必须自包含且可分享）
预设包的根目录结构：

text
preset_name/
├── manifest.json        # 格式版本、名称、作者、引擎最低版本、许可证声明
├── scene.json           # 元素树、图层、属性、绑定关系
├── interactions.json    # 动画、软件交互、系统规则的完整定义
├── resources/           # 图片、纹理、字体（可选）
└── preview.png          # 编辑器自动生成的缩略图
manifest.json 中必须包含 formatVersion 和 engineMinVersion，引擎在导入时做兼容性检查，不兼容时给出明确提示而不是静默失败。

开源承诺：scene.json 和 interactions.json 的 JSON Schema 文件与引擎代码一同在仓库中开源。社区可以基于 Schema 开发第三方预设生成器、预览器或格式转换器——这是未来“平台”能够生长的种子。

5. 开发顺序（严格遵守，不允许跳跃）
阶段 0：引擎骨架 + 预设格式

一个能显示单个静态元素的 WallpaperService。

scene.json 的 Schema v0.1 定稿。

不可见时停止渲染的 onVisibilityChanged 逻辑必须在此阶段完成。

阶段 1：属性编辑器闭环

画布拖拽、属性面板、保存/加载预设。

用户能做出一个“静止但可保存/导入”的壁纸。

此时还没有动画。

阶段 2：动画交互

时间轴、关键帧、缓动曲线、触摸触发动画。

用户能做出“点击元素后旋转/变色”的壁纸。

阶段 3：软件交互

启动应用、切换全局变量、屏幕滚动视差。

用户能做出“点击图标启动 App”或“滑动桌面产生视差”的壁纸。

阶段 4：系统交互

电池、电源、屏幕、网络、传感器变量接入。

用户能做出“电量越低颜色越红”或“陀螺仪控制视差方向”的壁纸。

阶段 5：预设分享与社区验证

导出/导入打磨、GitHub Discussions 预设交换流程文档化。

不急于建服务器。用文件手动交换来验证“用户是否真的有分享和导入他人预设的意愿”。

6. 代码生成与修改的强制规则
当你生成或修改任何代码时：

先检查是否触及预设格式。任何对 scene.json / interactions.json 结构的修改，必须同步更新 Schema 文件和导入导出兼容逻辑。

交互事件必须走统一总线。不允许在 onTouchEvent 或 BroadcastReceiver 中直接修改元素属性；必须发布规范化事件，由动画/规则系统消费。

渲染循环不可阻塞。传感器和广播回调只写入线程安全的状态变量，GL 线程按帧读取，避免在回调中执行绘制或复杂计算。

功耗意识写进每一行渲染代码。任何新效果实现后，必须回答：“壁纸不可见时，它是否产生了任何唤醒或绘制？”

开源可维护性优先。选择依赖库时，优先选 Apache 2.0 / MIT 许可证、活跃维护、无强制商业条款的库。不引入闭源 SDK 作为核心依赖。

不做超出阶段范围的功能。如果当前处于阶段 1，不要生成时间轴 UI；如果处于阶段 2，不要生成系统广播接收器。严格按第 5 节的顺序推进。
